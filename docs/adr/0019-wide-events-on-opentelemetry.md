# One wide event per request, built on OpenTelemetry

Every request the server handles prints one line of JSON when it ends: its wide event, also called a canonical log line. The event is the request's root OpenTelemetry span: the fields that code annotates while the request runs, and the sums of its child spans (database queries, outgoing calls, named units of work). A span processor in `packages/telemetry` builds the line when the root span ends, a tail sampler decides whether it is printed, and a privacy guard checks every field before it gets there. The same spans are exported to Vercel's trace collection and, when configured, to any OTLP collector. How to add to the event, the naming rules, the privacy rules and every field are in `docs/observability.md`.

## Why

Until now the server printed a few unrelated `console.error` lines: a tRPC failure, a photo storage failure, a share link that could not be looked up. Nothing said which procedures are slow, how many queries a request makes, how often a refusal happens or why, or which Stylist and app version a failure hit. The logs are where an agent will look for performance problems and things to correct, so they have to answer questions nobody has thought of yet. A single event per request with many fields, including IDs that are different for every request and the decisions the code took, answers them with one query and no joining of lines. Errors, slow requests and chosen Stylists are always kept by the tail sampler; the rest by a rate that is 1 today, because the app has about 250 requests a day.

Production runs on Vercel's Hobby plan, which keeps runtime logs for an hour; a cron job on the maintainer's server archives them every 15 minutes into `~/hcm-logs`. So the event has to be one line on stdout, with a stable, flat, documented set of fields that can be loaded into a database later.

OpenTelemetry gives us the request context without passing anything around (code deep in a helper can annotate the request it is part of), Prisma's and `fetch`'s spans for free, trace ids that match Vercel's own traces and an incoming `traceparent`, and an export path to Vercel Tracing, which is part of the Hobby plan (1 million span units a month, kept 3 days; this app uses far fewer). The wide event is built from the spans, so there is one source of truth and no second set of measurements to keep in step.

## Choices inside the design

- **`@vercel/otel` rather than the SDK set up by hand.** It is what Vercel and Next.js 16 document, it is the only setup with which Vercel's trace collection and Trace Drains work, and it bundles the SDK, so the app depends on `@opentelemetry/api` and little else at run time. It also runs in a plain Node.js server, so the dev backend uses the same setup. Its automatic export is only switched on where there is somewhere to export to (on Vercel, or with `OTEL_EXPORTER_OTLP_ENDPOINT`), because off Vercel it otherwise sends to an OTLP collector at `localhost:4318` that is not there.
- **Every request is traced (`always_on`).** The event is built from the root span, so a request whose caller sent a `traceparent` saying "not sampled" would otherwise have no event. What is printed is decided by our tail sampler, what Vercel keeps by its own sampling rules.
- **`@prisma/instrumentation` at the same version as Prisma (7.8).** With Prisma 7, the query compiler and the `pg` driver adapter, Prisma Client traces itself through a global hook that the instrumentation installs; it needs no patching of modules, so it works in Next.js's bundles. Its spans name the operation (`Client.findMany`) and time each SQL statement.
- **The privacy guard is code, not only a rule.** Key names that name personal data or contents are refused unless they name a measure (`notes_length`), strings are capped, and what looks like an email address or a phone number is blanked. A mistake in an annotation shows up as `telemetry.blocked_keys` instead of a phone number in a public log archive.
- **Telemetry never fails a request.** Every function swallows its own failures, and a failure is counted in the next event.

## Alternatives

- **Plain console logging, as before.** Free text lines are hard to search, say what the code did rather than what happened to the request, write IDs in different forms in different places, and come several to a request with nothing to join them. They tell nothing about requests that went well, which is where performance problems are.
- **A log drain on Vercel Pro.** Drains keep logs and traces longer and send them to a log service, but cost a paid plan for an app with one user, and would still carry whatever the app prints. The archive the maintainer already runs does the keeping; what was missing is what the app prints.
- **A hosted error tracker (Sentry and the like).** Good at grouping exceptions, but it sees failures and not the requests that succeed slowly or are refused, keeps the data with another company, and its SDK sets up OpenTelemetry its own way, which conflicts with `@vercel/otel`. The wide event keeps the error with its stack next to the request's other fields.
- **Structured logging of many lines per request.** JSON lines are searchable, but a request is still spread over several lines that have to be joined by a request id, and the business context ends up on whichever line happened to have it. One event per request, built up as the request runs, is the point.
